# Elhafez Tourism v32.5.7 — Customer Hardened

## هوية الحزمة
هذه الحزمة مخصصة **للعميل Customer فقط**. إدارة المالك والاشتراكات والتجديد والترخيص والنشر تتم من **Elhafez Technology Owner Center** المنفصل. لا توجد واجهة Owner/Vendor تشغيلية داخل Runtime العميل.

## ما تم إصلاحه في هذه المرحلة
- توحيد رقم الإصدار إلى 32.5.7 في الويب والخادم وAndroid وملفات الحزمة.
- استبعاد Vendor Admin server/UI فعليًا من Customer build مع الإبقاء فقط على مفتاح/Agent الربط اللازم للتحقق المركزي من الترخيص والتحديث.
- إزالة Bearer session token من `localStorage` في Android والاعتماد على HttpOnly cookie الموجودة بالخادم.
- عدم إعادة `tokenHash` الكامل في قائمة الجلسات الإدارية.
- Rate limiting لمحاولات تسجيل الدخول أصبح PostgreSQL-backed بدل ذاكرة Node المؤقتة.
- Factory Reset لا يمحو سجل `erp_audit_events`؛ يسجل حدث `factory-reset` للمراجعة.
- Android Release يرفض إنتاج Release غير موقّع عند غياب متغيرات التوقيع.
- `verify` يشغل كل ملفات Node `*-smoke.mjs` تلقائيًا + اختباري المتصفح ثم يبني الخادم.
- تحديث اختبارات قديمة كانت تتوقع إصدارًا/واجهة Owner قديمة أو سلوك UI تم تغييره لاحقًا.
- إضافة اختبار أمان وإصدار خاص بـ v32.5.7.
- إزالة `@ts-nocheck` من مجموعة ملفات ثبت أنها تجتاز TypeScript دون تغيير سلوكها.

## نتيجة الفحص المحلي لهذه الحزمة
- Node smoke tests: **39/39 ناجح**.
- Browser smoke suites: **6/6 ناجح**، وتشمل اختبار قوائم ببيانات كثيفة واختبار إجراءات العملاء/الموردين/المندوبين.
- Frontend TypeScript build: ناجح.
- Server TypeScript build: ناجح.
- الحزمة المصدرية لا تحتوي على `node_modules`؛ يجب استخدام `npm ci` في بيئة البناء كالمعتاد.

## ما لم يتم اعتباره منتهيًا بعد
هذه العناصر تحتاج مشروع انتقال تدريجي لأنها تغييرات بنيوية عالية المخاطرة، ولا يجوز تنفيذها كتعديل جماعي داخل إصدار واحد ثم الادعاء أن النظام لم يتأثر:
- الحالة التشغيلية الأساسية ما زالت تعتمد بدرجة كبيرة على `erp_state.payload` كـ JSONB مركزي؛ يلزم نقل تدريجي للكيانات المالية والتشغيلية إلى جداول مترابطة مع Compatibility/Migration واختبارات reconciliation.
- لا يزال هناك دين UI في `src/styles.css` واستخدامات `!important` وinline handlers؛ تنظيفها يجب أن يكون شاشة/مكوّنًا بمكوّن مع Visual Regression. اختبار المتصفح الحالي أثبت سلامة المسارات المختبرة لكنه لا يعادل Visual Regression شامل لكل شاشة.
- ما زالت بعض الوحدات الكبيرة وبعض الملفات تستخدم `@ts-nocheck`؛ يجب تقليلها على دفعات مع typecheck واختبارات بعد كل دفعة.
- لم تُنفذ داخل هذه الحزمة اختبارات PostgreSQL حقيقية متعددة المستخدمين أو Load test 20–50 مستخدمًا، ولا SAST/SCA، ولا بناء AAB موقع فعليًا بمفاتيح Google Play.

## قرار الاستخدام
هذه النسخة أفضل وأصلب من v32.5.6 كـ **Customer hardening checkpoint**، لكنها لا تُعلن كنسخة “خالية من الأخطاء/جاهزة للبيع نهائيًا” قبل إغلاق البنود البنيوية أعلاه على بيئة Staging حقيقية.
