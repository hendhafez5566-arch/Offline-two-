# نموذج التخزين — تصميم الجزء 5 (مسودة للموافقة، لم يُنفَّذ)

> الحالة: **تصميم + أدوات تحقق فقط.** ما اتغيّرش أي كود إنتاج في التخزين. السبب: مفيش PostgreSQL ولا build كامل في بيئة الكتابة، والنقل من غير تجربة فعلية على بيانات حقيقية ممنوع (بند "ما تقولش اشتغل وإنت ما جرّبتش").

## 1) الوضع الحالي (من قراءة الكود)
- `erp_state(tenant_key, payload jsonb, revision, storage_mode, entity_row_count, entity_present_keys)`: JSON واحد لحالة الشركة.
- `erp_entity_records(tenant_key, collection_key, entity_id, ordinal, branch_id, record_date, status, record_no, party_id, program_id, data jsonb)`: **صف لكل سجل** لـ42 مجموعة (عملاء، موردين، مندوبين، عروض، أوامر شراء، برامج، حجوزات، مسافرين، خدمات، فواتير، تسويات، سندات قبض/صرف، مصروفات، تحويلات، شيكات، عمولات، قيود، مسودات قيود، جرد خزينة، تسويات بنكية، فروق عملة، موافقات، و20 مجموعة عمرة). عليها فهارس (فرع/تاريخ/حالة/طرف/برنامج + GIN على data).
- `storage_mode`: `entity-backed` (المجموعات في الصفوف فقط، والـpayload فيه الباقي) أو `legacy-full` (كل شيء في JSON، والصفوف مرآة). الكتابة بتقع في `legacy-full` لو أي سجل بلا `id` أو id مكرر، أو عدد الصفوف ≠ المتوقع (`entityBackedWritePlan`).
- المتبقي في `payload` بعد التجريد: الإعدادات، المستخدمون (`users`)، الفروع، الخزائن/الحسابات، الترخيص، الـmeta، المرفقات (بيانات وصفية).
- العميل: IndexedDB باسم `APP.dataDb` (إصدار 1، store واحد `state`، مفتاح `main` = نفس JSON)، وlocalStorage لمفتاح `erp_professional_suite_v32_2_commercial_offline` ونسخة اسم الشركة/الشعار (`erp_public_brand_v1:<tenant>`)، وsessionStorage للجلسة.

## 2) أهم استنتاج
**الجداول "الحقيقية" موجودة فعلًا بشكل Document-per-row.** يعني مش محتاجين نكتب 42 جدول جديد علشان نوحّد المصدر. الأقل خطرًا:

| المرحلة | الوصف | الخطر |
|---|---|---|
| A | نخلي `entity-backed` هو الوضع الوحيد: أي شركة `legacy-full` تترحّل بالأداة (dry-run ← backup ← transaction ← تحقق). الكتابة ترفض بدل ما ترجع لـlegacy-full لو سجل بلا id/مكرر (بعد تنظيفه) | متوسط: لازم PostgreSQL للتجربة |
| B | طبقة repository واحدة (`server/src/repository/`) فيها `load(tenant)`, `save(tenant, payload, expectedRevision)`, `readCollection`, `upsert`, `delete`، ونحوّل `state.ts` و`entity-mirror.ts` لاستخدامها. بدون تغيير الجداول | منخفض |
| C | **اختياري ولاحقًا:** جداول علائقية حقيقية للقيود وبنودها فقط (`journal_entries`, `journal_lines`) لو احتجت استعلامات تقارير بالـSQL. باقي الكيانات تفضل document-per-row | عالي: ده يمس المحاسبة، ما يتعملش من غير موافقتك |

## 3) لماذا لا نفرد كل كيان في جداول علائقية الآن
منطق المحاسبة كله في الواجهة بيشتغل على JSON كامل (`DB.data.*`)، والخادم بيدمج التغييرات المتزامنة على مستوى المجموعة (`state-merge.ts`). تفكيك 42 كيان لأعمدة يعني إعادة كتابة طبقة الدمج + الواجهة، وده خارج "بدون تغيير سلوك". والـ`data jsonb` بيحفظ كل الحقول فمفيش فقد بيانات.

## 4) الجداول المقترحة (للمرحلة A/B — بدون جداول جديدة، إضافة فقط)
- **لا تغيير** في `erp_entity_records` و`erp_state` (migrations 001..013 ما تتلمسش).
- Migration جديد `014_entity_only_guard.sql` (يُكتب بعد الموافقة): `check`/trigger يمنع `storage_mode='legacy-full'` لشركة فيها صفوف، وفهرس مركّب `(tenant_key, collection_key, record_date desc)` لو القياس أثبت إنه مفيد.
- الإعدادات والـblobs الصغيرة تفضل في `erp_state.payload` (حجمها صغير بعد التجريد). المرفقات الكبيرة في `erp_file_refs`/الملفات كما هي.

## 5) الترحيل — أدوات مكتوبة (غير مُجرَّبة على PostgreSQL)
الأدوات (كلها في `scripts/`):
- `lib/state-verify.mjs` + `state-verify-cli.mjs`: بصمة ومقارنة (عدد السجلات، hash لمحتوى كل سجل، ميزان المراجعة وأرصدة الأطراف لكل عملة، المدين = الدائن).
- `lib/migration-plan.mjs`: الخطة (تحقق من id مفقود/مكرر/مجموعة مش مصفوفة، تجريد الـpayload، إعادة التجميع). **متجرّب**.
- `lib/migration-runner.mjs`: التنسيق (dry-run، apply داخل transaction، backup، تحقق، verifyAfter، rollback، restore). **متجرّب على قاعدة وهمية في الذاكرة** بسلوك transaction حقيقي.
- `state-migrate-cli.mjs`: وصلة PostgreSQL (SQL فعلي). **ما اتشغلش على PostgreSQL، فحص syntax بس.**

الشروط اللي طلبتها وإزاي اتحققت:
| الشرط | التنفيذ |
|---|---|
| (أ) dry-run | الافتراضي، `begin read only`، بيطبع: جاهز/محجوب، الأسباب، عدد الصفوف، وهل المرآة الحالية = الـpayload |
| (ب) نسخة احتياطية | صف كامل (payload + revision) في `erp_state_migration_backup` قبل أي تغيير. وانت خد `pg_dump` كمان |
| (ج) transaction | كل شيء في `begin/commit` مع `select … for update` (نفس قفل الكتابة العادية). أي فشل = rollback |
| (د) تحقق | عدد الصفوف، hash المحتوى، ميزان المراجعة وأرصدة الأطراف قبل = بعد، المدين = الدائن، وبعد الـcommit تحقق مستقل `--verify`. لو مصدر القيود نفسه غير متوازن الترحيل بيرفض |
| (هـ) ما تحذفش القديم | الـpayload الأصلي كامل في جدول النسخ، ومحدش بيمسحه غيرك. الترحيل ما بيغيّرش `revision` فالعملاء ما بيتعملهمش resync |
| (و) rollback | `--rollback`: يرجّع للوضع القديم من الصفوف الحالية (بيحافظ على اللي اتحفظ بعد الترحيل). `--restore-backup ID --force`: يرجّع الـpayload القديم بالحرف (بيضيّع أي تغيير بعده، فلازم force) |

**ما اتغيّرش:** لا migration SQL جديد (الجدول بيتعمل من الأداة)، ولا تحويل لـ`state.ts`/`server.ts`، ولا إزالة `legacy-full`. السبب: إزالة الوضع القديم ما ينفعش قبل ما تجرّب الأداة على بياناتك. بعد ما تعدّي، الخطوة الجاية: فرض `entity-backed` فقط في `entityBackedWritePlan`، وتحويل الاستدعاءات لـ`server/src/repository/state-repository.ts` (موجود، رفيع، غير موصول).

## 6) التخزين المحلي على الأندرويد/المتصفح
- هو **IndexedDB/localStorage على الجهاز**، ومش مرتبط بجداول السيرفر. الصيغة = نفس JSON لحالة الشركة (store `state` / مفتاح `main`).
- القرار المقترح: **يفضل منفصل وبصيغته الحالية.** مفيش سبب لتغييره في المراحل A/B لأن السيرفر هو اللي بيتغيّر داخليًا والـAPI بتفضل بنفس الشكل (`clientPayload`). لو اتغيّرت الصيغة لاحقًا، المطلوب ترحيل تلقائي عند أول تشغيل مع الاحتفاظ بالنسخة القديمة حتى النجاح.
- لا يوجد تغيير مقترح، فلا يوجد ترحيل مطلوب على الموبايل في هذه المرحلة.

## 7) ما لم يُقَس
الأداء (زمن تحميل/حفظ قبل/بعد) لم يُقَس: يحتاج PostgreSQL وبيانات كبيرة. الفهارس الحالية موجودة ولم أضف جديدًا بدون قياس.
