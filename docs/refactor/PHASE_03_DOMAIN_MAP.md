# Phase 3 domain map

Inspected at b6569036062b5b2c775631face10c06dcdc9a2e5 before client edits. The client uses ordered global scripts, not modules. A name ending in Actions is not automatically business code: actual method bodies were inspected.

| Domain | Actual business flow and state | Dependencies and accounting effects | Phase 3 boundary |
|---|---|---|---|
| CRM / Commercial | Lead conversion to customer; followups; quotation draft/sent → accepted → converted; branch/user rules | CRM owns records in DB; followup records capture Auth user; quotation conversion creates and posts customer invoice | Typed lead/quotation use cases; lifecycle rules; live repository and actor ports |
| Tourism | Service draft → confirmed → completed/reopened; non-draft edits lock financial fields; bookings coordinate rooms/travelers | Transactions calls inventory, customer/supplier invoice posting and commission coordination; financial fields cannot change after posting | Separate lifecycle and room rules; invoice/voucher rules reused by financial paths |
| Procurement / Suppliers | PO draft → approved → partiallyReceived/received → partiallyInvoiced/converted; void/remove restrictions | PO fulfillment preserves received/invoiced quantities; conversion posts supplier invoice, links advances; Umrah commitments forbid independent void | Purchase use cases + fulfillment/lifecycle rules; legacy linked-document patch order retained |
| Hajj / Umrah | Program planning/contracting/pricing/open/salesClosed/operating/traveling/returned/closed; booking readiness/travel sequence; discount/capacity constraints | UmrahCore_DB is an existing live central-state adapter; Bridge authorizes and emits ERP integration events; procurement creates linked POs | Pure transition, discount, pricing and payment-status rules; existing financial bridges retained |
| Finance / Accounting | Receipt/payment allocation and FX; approval before treasury/allocation mutation; invoice post/cancel; journals/reversals/transfers | Accounting.post validates each line, rounds base values then checks balance; advanced expenses/deferrals/accruals/assets/loans/payroll/opening balances use this same engine | Voucher use cases and posting rules; shared journal/invoice rules used by all accounting domains; advanced scheduling/calculation rules |
| Reports / Control | P&L excludes year-close/reopen, aging uses remaining invoice metrics, budgets compare actual by account nature | Insights and AdvancedAccounting query ledger; printing embeds HTML and Actions name lookup | Typed query rules with supplied ledger/account/metrics; rendering retained |
| Administration | Approval self-approval/limit rules; branch access and stranding/last-active restrictions | Auth holds session; DB holds approvals/users/branches; branch selection persists local preference; audit records requester | Approval and branch use cases + actor/authorization/repository/preference ports |

Receipt and payment ordering is metadata validation → business validation → approval (payments) → treasury → allocation → journal → voucher/cheque → linked updates → document/audit. Invoice tax snapshots precede credit-limit validation; invoice status changes follow posting. Existing synchronous returns, transaction labels/options, error order and optional integrations are preservation constraints.

Presentation templates, modal callbacks, messages, PDF/export rendering, backup screens, native platform wrappers and global registrations are Phase 4 debt. The existing legacy facades/infrastructure adapters remain; extraction does not claim complete removal of all global coupling.
